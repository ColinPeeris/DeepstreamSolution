Triton Inference Server vs. native DeepStream nvinfer
Multi-stream LPR pipeline throughput benchmark
================================================================================

Date: 2026-09-15
Repository: DeepstreamSolution  (mount point in container: /workspace)
Full results: benchmarks/results/results.csv (per repeat) and summary.txt


--------------------------------------------------------------------------------
1. INTRODUCTION
--------------------------------------------------------------------------------
This benchmark compares two inference backends for the same License Plate
Recognition (LPR) pipeline built on NVIDIA DeepStream SDK 8.0:

  * nvinfer  - DeepStream's in-process inference plugin. The 5 neural networks
               run directly inside the pipeline process on the GPU.
  * triton   - A locally running NVIDIA Triton Inference Server (v2.56.0)
               reached over gRPC localhost:8001 in place of every nvinfer
               element (the pipeline uses DeepStream's nvinferserver plugin).

The question answered is not per-inference GPU cost of a single model, but:
which backend lets the entire pipeline consume more frames per second while
processing 1, 16 and 32 identical 720p streams concurrently.

Both backends run the identical five-stage model chain:
  pgie_detector_1  TrafficCamNet (FP16, batch 16)            - primary detector
  sgie_lpd_2       LPDNet (INT8, batch 16)                   - plate detection
  sgie_lpr_3       LPRNet (FP16, batch 16) + custom NVPlate  - OCR of the plate
  sgie_classifier_5/6  VehicleMakeNet / VehicleTypeNet (FP16)- vehicle attributes
plus the NvDCF tracker and OSD. The Triton model repository serves the same
five models (max batch size 16) built from the same weights.


--------------------------------------------------------------------------------
2. METHODOLOGY
--------------------------------------------------------------------------------
2.1 Environment
  GPU           : NVIDIA GeForce RTX 3080 Ti, 12 GB, driver 580.173.02, CUDA 12.8
  DeepStream    : 8.0.0 (image build 2025-08-01), GStreamer 1.24.2, Python 3
  Triton        : 2.56.0 (model repo: /workspace/triton/model_repo, gRPC 8001)
  Container     : ds_triton (root), repository bind-mounted at /workspace

2.2 Input
  Each stream replays the same clip
    /opt/nvidia/deepstream/deepstream/samples/streams/sample_720p.h264
  (1920x1080 H.264, 1441 frames). For N streams the pipeline decodes N copies
  concurrently through N hardware decoders into one nvstreammux; total
  processed frames = N * 1441 (1441 / 23056 / 46112 for N = 1 / 16 / 32).

2.3 Configs under test (auto-generated by benchmarks/make_configs.py)
  benchmarks/configs/lpr_nvinfer_1.json / _16 / _32
  benchmarks/configs/lpr_triton_1.json  / _16 / _32
  Generated by copying the canonical LPR configs
  (configs/detector_tracker_classifier_lpr_deepstream_8.json and its
  lpr_triton..._8.json counterpart) and applying, to BOTH backends identically:

    * video_source.filenames = [VIDEO_FILE] * N  (1, 16 or 32 entries)
      - For N > 1 the config passes a list of files to play; each entry gets
        its own filesrc / h264parse / nvv4l2decoder chain wired to
        streammux sink_<i>.  In a real deployment each path would point to a
        different camera; for this benchmark the same 1441-frame clip is
        repeated N times so decode cost scales linearly.
      - The single-entry configs use the original "filename" string instead,
        keeping full backward compatibility with every existing pipeline
        config in the repository.
    * video_source.streammux_batch_size = min(N, 16)
      -> each streammux buffer carries up to 16 frames, so the GIE models
         actually execute at their configured batch-size 16 (matching the
         Triton repo max_batch_size). At 1 stream the muxer still emits
         1-frame buffers (batch-size 1) as before.
    * sink_type = "fakesink"          -> the filesink branch adds a CPU
         avenc_mpeg4 encoder that bottlenecked at 16-32 streams; it is
         removed so the measurement reflects decode+track+infer, not encode.
    * va_filters = []                 -> the VA event filters publish per-frame
         metadata to RabbitMQ (va_filter_builder.send_metadata); disabled to
         remove unrelated per-frame publish latency.

  Every other element (streammux dimensions, model configs, tracker, OSD,
  nvstreammux width/height 1920x1080) is identical for both backends.

2.4 Runner (benchmarks/run_benchmark.py)
  For each config:
    1 warm-up run (discarded) followed by 3 measured runs.
    The wall-clock from process launch to exit (End-of-stream on the bus) is
    the end-to-end pipeline time; fps = N*1441 / wall_s.
    Per-model timings come from InferenceTimingMonitor (Utils/timing.py): a
    probe on every GIE src pad measures the interval between consecutive
    output buffers (per-batch interval); divided by the model's configured
    batch size it yields per-image time.
  Triton management for single-system fairness:
    * before triton configs: the server is started (models loaded, gRPC
      listens on 8001) and left running;
    * before nvinfer configs: the server is stopped so nvinfer never competes
      with a loaded Triton for GPU memory/cycles.
  All runs share the GPU with the pipeline's hardware decoders; no other
  processes ran during measurement.

2.5 Note on the 1-stream per-image figures
  Streaming with 1 stream = 1-frame buffers, but the timing monitor divides
  the batch interval by the configured batch size 16; its "per_image" for the
  1-stream case is therefore 16x too small and must not be read literally.
  The 16/32-stream numbers are true per-image costs because every buffer
  carries 16 frames. End-to-end fps is exact in every case.


--------------------------------------------------------------------------------
3. RESULTS
--------------------------------------------------------------------------------
3.1 End-to-end throughput (whole pipeline, fakesink, mean of 3 runs)

  Backend  Streams  Wall time (s)   Frames     FPS (mean)  Per-run fps
  -------  -------  ------------   -------    ----------  ------------
  nvinfer     1        4.62          1 441        316       329 / 308 / 312
  nvinfer    16       27.18         23 056        848       856 / 845 / 844
  nvinfer    32       50.04         46 112        922       923 / 921 / 921
  triton      1        5.23          1 441        276       276 / 276 / 276
  triton     16       23.97         23 056        962       968 / 960 / 958
  triton     32       43.03         46 112       1072      1073 / 1072 / 1070

  Throughput scaling vs. the same backend at 1 stream (xN):
    nvinfer: 16 -> 2.68x, 32 -> 2.91x
    triton : 16 -> 3.49x, 32 -> 3.89x

  Triton relative to nvinfer (fps_ratio):
    1 stream : 0.87x (Triton slower by ~13%)
    16 streams: 1.13x (Triton ~13% faster)
    32 streams: 1.16x (Triton ~16% faster)

3.2 Per-image inference cost (true at 16/32 streams: 16-frame batches)

  Backend  Streams  pgie    sgie_lpd   sgie_lpr   make      type
                   (ms/img) (ms/img)   (ms/img)   (ms/img)  (ms/img)
  -------  -------  ------  --------   --------   -------   -------
  nvinfer    16      1.08     0.88       0.88       0.88      0.88
  nvinfer    32      1.04     0.93       0.93       0.93      0.93
  triton     16      0.95     0.75       0.75       0.75      0.75
  triton     32      0.89     0.78       0.78       0.78      0.78

  Per-batch intervals (16 frames, pgie): nvinfer ~17.5 ms, triton ~15.2 ms
  at 16 streams, i.e. Triton amortizes the batch at ~14% lower interval.

3.3 Observations
  - The primary detector dominates GIE cost; the three secondary stages ride
    the same frame cadence and report near-identical per-image numbers.
  - Triton's advantage grows with stream count: with a loaded gRPC/Triton
    stack the server-side TRT-engine scheduling and coarse-grained batching
    inside Triton beat in-process nvinfer at 16 and 32 streams.
  - At a single stream Triton's per-request gRPC overhead on 1-frame batches
    is not amortized, so nvinfer is faster (316 vs 276 fps).
  - First Triton inference after server start took ~292 s (one-off engine
    build); after warm-up every Triton run was steady (5.2 s for 1 stream).
  - 32 streams ran on the 12 GB RTX 3080 Ti without OOM; no memory pressure
    or decoder errors observed in any run. All runs exited rc=0 with
    End-of-stream on every config.


--------------------------------------------------------------------------------
4. CONCLUSION
--------------------------------------------------------------------------------
For a single stream, the native nvinfer path is faster (~316 fps vs ~276 fps)
because there is no gRPC round-trip to amortize. As soon as the pipeline
batches several streams (16 or 32), the Triton backend out-processes nvinfer
by ~13-16% end-to-end (962 vs 848 fps at 16 streams; 1072 vs 922 fps at 32)
and shows better scaling with stream count (3.9x vs 2.9x from 1 to 32
streams). The Triton architecture pays off exactly where a multi-stream
video analytics server wants it: amortized batch inference across concurrent
streams. nvinfer remains the leaner choice for single-camera pipelines.

5. REPRODUCTION
--------------------------------------------------------------------------------
Environment: the DeepStream 8.0 container with /workspace bound to the repo;
the Triton model repo already generated at triton/model_repo (see readme).

1) Generate the test configs:
     python3 benchmarks/make_configs.py

2) Run the full benchmark (auto-starts/stops Triton, warm-up + 3 repeats):
     python3 benchmarks/run_benchmark.py --all --repeats 3 --warmup

   Subsets / manual control:
     python3 benchmarks/run_benchmark.py --backend triton --streams 16 32
     python3 benchmarks/run_benchmark.py --no-manage-triton ...   (manual server)
   Manual server start for instrumenting:
     /opt/tritonserver/bin/tritonserver --model-repository=/workspace/triton/model_repo \
         --grpc-port 8001 --http-port 8000

3) Results: benchmarks/results/{results.csv, summary.txt, *_{1,16,32}_rep{1..3}/*.log}

4) Regenerate CSV/summary from saved logs without re-running:
     python3 benchmarks/run_benchmark.py --reparse

Caveats when interpreting:
  - 1-stream "per_image" column understates cost by 16x (see 2.5); use fps.
  - Enabled va_filters/RabbitMQ forwarder and the filesink MPEG4 encoder are
    deliberately disabled in the generated benchmark configs (see 2.3) - both
    would add identical-but-large constant cost to both backends.
  - Triton runs are single-server, single-GPU, same-machine; not a network
    deployment test.

Relevant source changes for the benchmark:
  - Modules/video_source_builder.py: multi-stream sources (N filesrc/h264parse/
    nvv4l2decoder chains -> streammux sink_<i>), configurable
    streammux_batch_size (default min(num_streams, 16)).
  - benchmarks/make_configs.py, benchmarks/run_benchmark.py: config generator
    and runner described above.
